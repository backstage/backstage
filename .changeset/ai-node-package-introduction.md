---
'@backstage/ai-node': minor
---

Added a new `@backstage/ai-node` package with an alpha, plugin-scoped AI service that gives backend plugins a managed, low-level agent primitive: each plugin chooses its own configuration path in app-config, sessions are bound to their original owner, and callers acquire reference-counted handles whose release never cancels admitted work. Model dispatch is guarded per attempt — permission, lease fencing, and credential identity are rechecked before any provider request, and every decision and outcome is recorded in a durable, redacted audit journal. Plugins can persist agent sessions in their existing PostgreSQL or file-backed SQLite database and recover committed state after a backend restart, with fenced writes that prevent expired or superseded owners from changing a session. Organization- and service-scoped provider credentials can be supplied as read-only secrets from app-config (each entry's credential kind is checked at startup against the modules registered for that provider, so a kind no module consumes rejects before the service starts), users can store personal provider credentials encrypted in the Backstage database with concurrent updates and OAuth refreshes serialized across replicas, and an installation-scoped `ai` config section supplies the canonical model catalog and credential precedence, with every missing entry failing closed as a journaled, actionable denial instead of a fallback.

Providers are registered as trusted in-process modules whose operations the guard certifies; the package itself is registration-only — it ships no provider modules, and hosts compose it with the extracted family packages (`@backstage/ai-node-provider-google`, `-openai`, `-anthropic`, `-azure`, `-typesafe`, `-openrouter`). A module-authoring entry point (`@backstage/ai-node/modules`) exports the provider and auth module contracts, the shared request-envelope validator, the OAuth token-request helpers, and the certification and guard-construction machinery the family packages build on — the provider certification registrar, the provider registry, the guard and journal constructors, and the guarded model operations — so provider packages and hosts can certify modules against the real guard. The test utilities that drive that machinery — the crash fixture, the journal harness, and a fixture registry of synthetic provider module copies — ship in the separate `@backstage/ai-node-test-utils` package. The guarded, journaled OAuth token-request modules for the Anthropic and OpenAI token endpoints live in their provider packages and travel on the family's provider modules, so registering a family registers its OAuth path with it. Pre-dispatch refresh is configuration-driven: declaring both the provider's trusted endpoint and its public OAuth client ID under `ai.credentials.tokenEndpoints` makes the stock factory wire refresh itself — a dispatch whose personal OAuth credential is at or inside the refresh window performs one journaled `auth.token` operation, writes the rotated credential to the store it came from and re-reads the authority before sending. Either half missing keeps the previous behavior, an expired credential failing closed with an actionable denial naming what is missing. A failed refresh denies the dispatch and journals the denial with nothing sent; the remote exchange and the local write are separate steps, so a crash between them is an uncertain rotation requiring re-authentication and carries no exactly-once claim. Installation-scoped credentials stay read-only and are never refreshed. Custom deployments can override the default with the alpha `CredentialRefreshHook` plus `createCredentialRefreshHook`, which assembles the same guarded machinery over a host's own modules or transport. The `tokenEndpoints` configuration shape is one entry per provider (`url` plus public `clientId`); it changed from the bare-URL form of this unpublished surface. Hosts can expose the managed service over HTTP through a support surface that enforces session ownership, model listing, and audit-read permissions. Fail-closed boundaries to be aware of: AWS Bedrock models are not supported and fail closed; the Codex transport dispatches over SSE only, with the WebSocket and automatic transports denied; and user-scope encrypted personal credentials are stored per plugin instance, so a user's personal credentials saved through one plugin are not shared with another plugin's instance.

Observability rides the root-shared Backstage events service: the service publishes typed, secret-free events — denials, dispatched operations, lease activity, and journal appends — to the `ai.observability.*` topics, fire-and-forget, with a throwing or rejecting publish consumed so observation never couples to what it observes. Hosts subscribe with the metrics subscriber and evaluate health from its snapshot — denial rate, lease contention, mean dispatch latency, and journal decision volume, each against a tunable threshold — as a pure, fail-open read that never gates dispatch; the AI backend plugin exposes that evaluation as an unauthenticated readiness endpoint returning 200 when ok and 503 when degraded.

Code mode is disabled by default; hosts enable it with an option that takes a host-supplied extension factory — the default construction, Pi's `codemode` extension over a bounded QuickJS sandbox, is the new `@backstage/ai-node-codemode` package — and the stock service factory passes the option through to the integration. With that default builder, scripts run with no access to the network, filesystem, timers, or host modules, and survive restarts by deterministic replay; a host wall-clock ceiling per script execution (default five minutes; a script's own declared timeout may lower it, never exceed it) and an optional memory limit bound runaway scripts; output, the retained script store, and replay journaling grow with the results a script's nested calls deliver; and model calls from inside scripts route through the same guarded facade as any other dispatch, with the per-attempt permission, fence, and credential recheck. These isolation, limit, and replay guarantees attach to the default builder: the core only resolves the limits, appends the returned extension, and closes the returned sandbox, so a custom factory receives the resolved limits and is trusted with its own sandbox's behavior — a custom extension need not have a durable journal at all. With the default builder, code mode's own durable journal lives in the conversation's storage and is separate from the AI audit journal.

The personal credential encryption key can be rotated: configure the new key with `rotation.previousEncryptionKey` carrying the old one, and during the dual-key window a read of an old-key credential re-encrypts it under the new key while new writes use it; failed decryptions and writes fail closed. A host that already owns a live namespace fence can proactively re-encrypt the whole plugin database through the rotation handle the installation wiring returns, which reports only inspected and rotated counts. The stock service exposes no maintenance fence — a public maintenance surface is future work — and rotation never touches other plugins' databases or returns credential values.

Hosts can schedule the journal prune on the backend scheduler service, applying the existing retention contract on a recurring task with its timeout at 80% of the frequency; one pass also runs immediately on start. Uncertainty records are committed before any deletion; deletes run in bounded chunks, each its own transaction, which limits the number of selected IDs per delete transaction and permits a concurrent journal append to interleave between chunks (the selection transaction that documents uncertainty first is not itself bounded); a failed pass is warned when a logger is supplied and retried at the next interval; aborting the schedule's signal stops it, with a straggler task run a no-op that never rejects. A stopped or failed pass reports zeros that mean "not measured", never "the journal holds none". Audit-read denials and missing sessions surface as the shared `@backstage/errors` `NotAllowedError` and `NotFoundError` classes.

Tool servers register as modules on the stock service factory: each declared tool becomes a guarded, journaled dispatch mediated exactly like model dispatch — per-attempt permission, fence, and credential recheck, envelope validation against the final request, and only certified destination routes — using the server's scoped credential from the reserved `mcp:` namespace, which can never be reached through a model provider id. Tool dispatch is authorized against one fixed `ai.tool.use` permission, with the tool identity and the requesting plugin evaluated against the policy's `isTool`, `isServer` and `isPlugin` conditions inside the guarded tool operations: the plugin id comes from the session namespace, so a policy can scope tools per plugin. The default factory registers none. The same seam carries a second kind of server: a **local** tool server declares `run(input)` instead of a destination, and the guard's local branch dispatches it after the decision, the fence check and the per-attempt `ai.tool.use` recheck, journaling the outcome by identity with no destination. That branch applies only to a module whose registered adapter is local — an HTTP module cannot reach it, and one that claimed it fails loudly rather than silently losing transport accounting. The narrowing is deliberate and documented: for a local module the guard's guarantee is journaled decision, fence and permission before execution, while the function itself runs with the backend process's privileges and the guard cannot constrain what it does. Command arguments and other free text are never journaled — the same rule that keeps prompts and payloads out, because free text cannot be proven secret-free. `@backstage/ai-node-shell` ships the reference local server.

Usage accounting is host surface: hosts construct the reader over the audit journal — the decisions and outcomes already enforced per dispatch — and aggregate it into time-windowed, grouped reports. It adds no enforcement of its own and records no durations. Queries name session ids, or enumerate namespaces through a host-supplied enumerator; without one, a query that names no sessions fails closed with an actionable error rather than enumerating anything.

Custom gateway providers work as first-class entries: pi's catalog treats a gateway as its own provider, so an `ai.models` entry keeps its gateway provider id and base URL while naming a certified adapter in `api`. Module resolution keys on that adapter, credentials scope to the gateway's own provider id, and the destination must still be one of the resolved module's certified routes — a gateway whose base URL re-roots the API under its own path therefore fails closed with nothing sent, and certifying such a prefix is not supported yet. OAuth through a gateway is out of scope: a family without an OAuth module refuses an `oauth` credential and names `api_key` as the supported kind.

Model discovery reports canonical catalog descriptors — the identity pair plus adapter, type, context window, and output limit where the catalog entry carries them — filtered per pair by the caller's own credentials, through the existing models route as additive wire fields. The installation configuration now accepts `classifier` and `image` catalog entries in addition to `chat`, with each type's size fields following the pinned catalog shapes: a classifier requires its context window, an image entry carries none. Model and tool authorization use one fixed permission per resource kind — `ai.model.use` over the `ai-model` resource type and `ai.tool.use` over `ai-tool`. Each check asks the permission backend for one conditional decision on that permission with the caller's own credentials and sends no resource data: the model pair or tool identity the service already holds (`provider`, `modelId`, `type?`; `serverId`, `toolName`) never leaves the process. The policy's conditions come back and are evaluated there against those attributes, the way the catalog evaluates entity conditions. Granularity lives in the `isModel`, `isProvider`, `isModelType`, `isTool`, `isServer` and `isPlugin` rules, which `@backstage/ai-node/alpha` exports together with the matching conditional-decision helpers for policy authors; a policy that allows a permission without conditions therefore grants every cataloged model or every registered tool, and the default posture is deny. Harness features are exposed the same way: a plugin declares the features it needs when it opens a harness (`tools`, `codemode`), and the service authorizes each one against one fixed `ai.feature.use` permission over the `ai-feature` resource type with the `{ pluginId, feature }` attributes evaluated in process against the `isFeature` and `isPlugin` rules. A feature the service does not register fails closed with a registration reason rather than being silently omitted, and a denied feature rejects the open with a reason naming the feature and the plugin. Availability is snapshotted at admission like module registrations: a live harness keeps its features until its last handle releases, a fresh open evaluates again, re-opening a live session with a different declaration is rejected, and a plugin that requests nothing gets a harness with no feature surface. Because no policy is the permission framework's default allow, a registered feature reaches every plugin that requests it until a policy denies `ai.feature.use` — restricting features is deliberate deployment work, the same sharp edge as a blanket `ALLOW` on model and tool use.

Classification and image generation dispatch through certified provider modules like chat: TypeSafe System One and OpenAI Decisions for classification, and OpenRouter for image generation, each with its own envelope validation on the guarded transport — a dispatch that completes without a guarded send fails closed, and only certified route shapes are accepted. The audit journal's model attempt records carry decisions and outcomes and exclude image data; image blobs are never journaled. Image-bearing requests are bounded per request at the shared envelope cap, but persisted image history is a separate cost that the request cap does not bound: hosts enabling image attachments in higher layers must bound total persisted image bytes and history length themselves, because storage cost grows with the history.
