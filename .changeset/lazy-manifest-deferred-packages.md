Frontend plugins that are built as module federation remotes, with `package build --module-federation` or `package bundle`, now get a `backstage-manifest.json` file next to `mf-manifest.json`. The file is also written to the `dist` folder of frontend plugin and module packages by `package prepack`, so that published packages include it. It describes each exposed plugin and module in its `frontend` section, and whether the plugin can be deferred, which lets an app load the plugin on demand. Whether a plugin can be deferred is decided by analyzing its source code without running it, and the reason a plugin can't be deferred is recorded in the file together with the source location of the code that prevents it.

A plugin can be deferred only if each of its extensions is a page or sub-page made with `PageBlueprint` or `SubPageBlueprint`, or a utility API made with `ApiBlueprint`, all from `@backstage/frontend-plugin-api`. The `path` and `title` params of a page or sub-page must be literal values, and a `routeRef` must be one of the routes of the plugin. Params that are only used to create the element, such as `loader`, can be anything. Extensions made with any other blueprint, including the entity card and entity content blueprints, or with `makeWithOverrides`, and params that are not literal values, such as an `icon`, prevent the plugin from being deferred. The stand-ins of pages and sub-pages apply their `path` and `title` config from `app.extensions`, and other config for an element of a deferred plugin loads the plugin right after the app has started. Utility APIs made with `ApiBlueprint` are recorded in the manifest, so that they can be loaded on first use.
