Frontend plugins that are built as module federation remotes, with `package build --module-federation` or `package bundle`, now get a `backstage-manifest.json` file next to `mf-manifest.json`. The file is also written to the `dist` folder of frontend plugin and module packages by `package prepack`, so that published packages include it. It describes each exposed plugin and module in its `frontend` section, and whether the plugin can be deferred, which lets an app load the plugin on demand. Whether a plugin can be deferred is decided by analyzing its source code without running it, and the reason a plugin can't be deferred is recorded in the file together with the source location of the code that prevents it.

A plugin can be deferred if each of its extensions is made with the `make` method of a blueprint, or with `makeWithOverrides` whose factory only returns the original factory called with params. The factory of the blueprint is analyzed for the params of each extension, to find the data that the extension outputs besides its element and which config keys replace that data. Params and config that are only used for the element can be anything, while the data that is output must be literal values, such as the path of a page or a string filter of an entity card. This works for blueprints such as `PageBlueprint`, `SubPageBlueprint`, `EntityCardBlueprint` and `EntityContentBlueprint` without any changes to them. Utility APIs made with `ApiBlueprint.make` are recorded in the manifest, so that they can be loaded on first use.
