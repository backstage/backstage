# Security Review — pass1

Mode: brownfield, intent feature-new, scoped to the 65 files in `provenance.json` (base `f20fd9b59828`). Generated files (`/generated/`) and `report*.api.md` were not reviewed line by line. They come from the validated OpenAPI spec and API extractor.

## Summary

This change adds the `backstage.io/former-names` annotation, an unauthenticated-by-schema-only (JWT-or-anonymous, same as `by-name`) `GET /entities/by-former-name/{kind}/{namespace}/{name}` route, and client-side redirects in the catalog entity page and TechDocs reader. The new route gets credentials the same way as the existing routes (`httpAuth.credentials(req)`), and the auditor event is created before the read. The resolved entity is read through the permission filter in `AuthorizedEntitiesCatalog`, and every query is parameterised through knex. The redirect targets are in-app router paths built from route refs, so there is no open redirect. Location-state text is rendered as React text, so there is no XSS. No secrets, manifests or lockfiles were touched. Two design-level issues remain. Both need the ability to register or edit an entity's annotations: (1) the unfiltered "real ref exists" and "claimant count" checks give an existence oracle for entities the caller cannot read; (2) any entity can claim any former ref in any namespace or kind, so old links can be redirected to an attacker-controlled entity or its docs. Neither is critical.

## Passing checks

- Route guard: the new route uses `httpAuth.credentials(req)` like `by-name`. Its OpenAPI `security: [{}, JWT]` matches the existing routes, and the default auth policy applies.
- Authz on the returned entity: `catalogEntityReadPermission` is checked. DENY returns a null item and CONDITIONAL applies the filter through `entitiesBatch`. A miss and a deny both return the same 404.
- Audit: `auditor.createEvent` runs before the read, and `success` or `fail` is recorded. The event records the requested ref and `queryType` (the auditor service supplies actor and request).
- Injection: all DB access uses parameterised knex `where`. Path params are normalised via `stringifyEntityRef`. The search key cannot collide with entity fields, because the top-level schema has `additionalProperties: false`.
- Input hardening: `getEntityFormerRefs` never throws, drops malformed or `:`/`/`/whitespace parts, deduplicates, and skips the entity's own ref. Over-long values are skipped at indexing.
- Frontend: redirect URLs come from `entityRoute`, `viewTechdocLink` and `buildTechDocsURL` (internal paths) and go through react-router `navigate` (not an open redirect). `formerEntityRef` from `location.state` is type-checked and rendered as escaped React text.
- Client failure handling: errors from `getEntityByFormerRef` in `useEntityFromUrl` are swallowed, so the page falls back to "not found" and leaks nothing.
- Secrets: no hard-coded credentials in touched source, docs or changesets. The test fixtures use only fake entities, and the `fake-token` in `CatalogClient.test.ts` predates this change. The `.gitignore` change only adds `.sdlc/`.
- Docs: YAML examples contain only entity names and annotations, with no secrets.
- PII encryption, role masking and audit-table integrity: n/a, not in the touched set.
- JWT secret, password hashing, Helmet, rate limiting and the global error filter: n/a, not in the touched set. The new 404 message only echoes the normalised ref and goes through the existing error handler.
- Dependencies: no `package.json` or lockfile in the touched set, so unchanged. `npm audit` was not run.

## Required fixes before sign-off

- Medium: fix the existence oracle in `resolveFormerEntityRef` by applying the permission filter to the real-ref and claimant checks, or explicitly accept and document the trade-off.
- Low (advisory, may be accepted): decide whether cross-namespace or cross-owner former-name claims should be allowed. If they are, record the hijack risk in the annotation docs.
