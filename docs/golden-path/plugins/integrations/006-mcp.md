## Actions and MCP

### What are Backstage Actions and MCP?

The
[Backstage Actions Registry](../../../backend-system/core-services/actions-registry.md)
is a shared list of tasks that backend plugins know how to perform. Each
[**action**](../../../backend-system/core-services/actions-registry.md#action-structure)
has a name, a description, the information it needs, and the information it
returns. Registering an action once allows other Backstage features to use it.

The [MCP Actions backend](../../../ai/mcp-actions.md) makes selected actions
available through the
[Model Context Protocol (MCP)](https://modelcontextprotocol.io/docs/getting-started/intro).
MCP is a standard that allows an external tool, such as a coding assistant, to
discover and run actions provided by Backstage.

### What to expect

In this guide, an MCP client asks Backstage for the TODOs connected to a
Component:

```text
MCP client asks for a Component's TODOs
  -> Backstage runs todo.list-for-entity
  -> todo.read checks the signed-in user's access
  -> Backstage returns only the TODOs that user may read
```

MCP does not decide who is allowed to see a TODO. Backstage still applies the
same `todo.read` permission used by the Component page and Search.

You will start with a
[**read-only** action](../../../backend-system/core-services/actions-registry.md#optional-properties),
which looks up information without changing anything. Actions that create,
update, or delete data need additional
safety checks and are outside this walkthrough.

### Prerequisites

Before starting:

- Complete [Scaffolder](005-scaffolder.md) so your test Component has onboarding
  TODOs.
- Confirm that the auth frontend and auth backend are installed. Apps created
  from the current default template already include both.
- Choose an MCP client that can use Streamable HTTP and Dynamic Client
  Registration. These terms are explained when you configure the client.

## Registering a TODO action

### Step 1: Share the authorization helper

The Permissions chapter placed the `getTodoReadFilter` function inside the HTTP
router. Move it to `plugins/todo-backend/src/authorization.ts` so both HTTP
routes and Actions can call the same permission check:

```ts title="plugins/todo-backend/src/authorization.ts"
import type {
  BackstageCredentials,
  PermissionsRegistryService,
  PermissionsService,
} from '@backstage/backend-plugin-api';
import { NotAllowedError } from '@backstage/errors';
import { AuthorizeResult } from '@backstage/plugin-permission-common';
import { createConditionTransformer } from '@backstage/plugin-permission-node';
import { todoReadPermission } from '@internal/plugin-todo-common';
import { todoResourceRef } from './rules';

export async function getTodoReadFilter(options: {
  credentials: BackstageCredentials;
  permissions: PermissionsService;
  permissionsRegistry: PermissionsRegistryService;
}) {
  const decision = (
    await options.permissions.authorizeConditional(
      [{ permission: todoReadPermission }],
      { credentials: options.credentials },
    )
  )[0];

  if (decision.result === AuthorizeResult.DENY) {
    throw new NotAllowedError();
  }

  if (decision.result !== AuthorizeResult.CONDITIONAL) {
    return undefined;
  }

  const transformConditions = createConditionTransformer(
    options.permissionsRegistry.getPermissionRuleset(todoResourceRef),
  );
  return transformConditions(decision.conditions);
}
```

Update the HTTP routes to call this helper too. Keeping the check in one
function prevents HTTP and MCP from applying different permission rules.

### Step 2: Register `list-for-entity`

Register an action named `list-for-entity`. It accepts a Component reference
and returns the TODOs that the signed-in user may read:

```ts title="plugins/todo-backend/src/actions/createListTodosAction.ts"
import type {
  PermissionsRegistryService,
  PermissionsService,
} from '@backstage/backend-plugin-api';
import type { ActionsRegistryService } from '@backstage/backend-plugin-api/alpha';
import { stringifyEntityRef } from '@backstage/catalog-model';
import { NotFoundError } from '@backstage/errors';
import type { CatalogService } from '@backstage/plugin-catalog-node';
import { getTodoReadFilter } from '../authorization';
import type { todoListServiceRef } from '../services/TodoListService';

export function createListTodosAction(options: {
  actionsRegistry: ActionsRegistryService;
  catalog: CatalogService;
  permissions: PermissionsService;
  permissionsRegistry: PermissionsRegistryService;
  todoList: typeof todoListServiceRef.T;
}) {
  options.actionsRegistry.register({
    name: 'list-for-entity',
    title: 'List TODOs for a Catalog entity',
    description:
      'Lists TODOs associated with a Catalog entity when the caller belongs to an owning Group.',
    attributes: {
      destructive: false,
      readOnly: true,
      idempotent: true,
    },
    schema: {
      input: z =>
        z.object({
          entityRef: z
            .string()
            .describe('Entity ref in kind:namespace/name form'),
        }),
      output: z =>
        z.object({
          items: z.array(
            z.object({
              id: z.string(),
              title: z.string(),
              forEntityRef: z.string(),
              dueAt: z.string().optional(),
            }),
          ),
        }),
    },
    action: async ({ input, credentials }) => {
      const entity = await options.catalog.getEntityByRef(input.entityRef, {
        credentials,
      });
      if (!entity) {
        throw new NotFoundError(`Entity ${input.entityRef} was not found`);
      }

      const filter = await getTodoReadFilter({
        credentials,
        permissions: options.permissions,
        permissionsRegistry: options.permissionsRegistry,
      });
      const { items } = await options.todoList.listTodosForEntity({
        forEntityRef: stringifyEntityRef(entity),
        filter,
      });

      return {
        output: {
          items: items.map(({ id, title, forEntityRef, dueAt }) => ({
            id,
            title,
            forEntityRef,
            dueAt,
          })),
        },
      };
    },
  });
}
```

Register the action from the todo plugin by adding
`actionsRegistryServiceRef` to its initialization dependencies:

```ts title="plugins/todo-backend/src/plugin.ts"
import { actionsRegistryServiceRef } from '@backstage/backend-plugin-api/alpha';
import { createListTodosAction } from './actions/createListTodosAction';

// Inside env.registerInit:
deps: {
  actionsRegistry: actionsRegistryServiceRef,
  catalog: catalogServiceRef,
  permissions: coreServices.permissions,
  permissionsRegistry: coreServices.permissionsRegistry,
  todoList: todoListServiceRef,
  // ...existing dependencies
},
async init({
  actionsRegistry,
  catalog,
  permissions,
  permissionsRegistry,
  todoList,
}) {
  createListTodosAction({
    actionsRegistry,
    catalog,
    permissions,
    permissionsRegistry,
    todoList,
  });

  // ...existing initialization
}
```

The registry knows that this action belongs to the `todo` plugin, so its full
name becomes `todo.list-for-entity`. Including the plugin name prevents it from
clashing with similarly named actions from other plugins.

## Exposing the action through MCP

### Step 3: Configure the MCP Actions backend

Apps created from the current default Backstage template already install
`@backstage/plugin-mcp-actions-backend` in `packages/backend`. Confirm that the
backend includes:

```ts title="packages/backend/src/index.ts"
backend.add(import('@backstage/plugin-mcp-actions-backend'));
```

The following configuration lets the MCP Actions backend discover actions from
the todo plugin. It creates a focused MCP server that exposes only actions whose
names begin with `todo:`:

```yaml title="app-config.yaml"
backend:
  actions:
    pluginSources:
      - todo

mcpActions:
  servers:
    todo:
      name: Component TODOs
      description: TODO tools restricted to the Component's owning Groups
      filter:
        include:
          - id: 'todo:*'
```

The MCP client connects to this address using
[Streamable HTTP](../../../ai/mcp-actions.md#configuring-mcp-clients). This is
the current way an MCP client and Backstage exchange requests over the web:

```text
http://localhost:7007/api/mcp-actions/v1/todo
```

Do not configure the older, deprecated SSE address.

### Step 4: Enable Dynamic Client Registration

The MCP action must know which Backstage user is calling it so that
`todo.read` can check that user's Group ownership.
[Dynamic Client Registration](../../../ai/mcp-actions.md#dynamic-client-registration)
provides the sign-in flow. The MCP client opens Backstage in a browser, where
the user signs in and approves access. Backstage can then give the client access
on that user's behalf. The user does not need to copy a token into the MCP
settings.

Apps created from the current default template already include the auth backend
and the `@backstage/plugin-auth` frontend plugin. Enable registration in
`app-config.yaml`:

```yaml title="app-config.yaml"
auth:
  experimentalDynamicClientRegistration:
    enabled: true
    allowedRedirectUriPatterns:
      - cursor://*
```

The callback URI is the address to which Backstage returns the client after the
user approves access. Replace `cursor://*` with the callback URI pattern
documented by your MCP client. Restricting this value to the chosen client is
safer than allowing every callback address.

Then configure the client with the server URL and no authorization header:

```json
{
  "mcpServers": {
    "backstage-todos": {
      "url": "http://localhost:7007/api/mcp-actions/v1/todo"
    }
  }
}
```

On the first connection, the client opens the Backstage authorization page.
Sign in as the user who will use the tools and approve the request. Backstage
then gives that MCP client the user's permitted access.

Dynamic Client Registration is highly experimental. It makes this local
walkthrough easier because users do not have to copy tokens, but review its
limitations and allowed callback addresses before enabling it in production.
See the
[MCP Actions backend authentication documentation](../../../../plugins/mcp-actions-backend/README.md#authentication-configuration)
for current details.

### Step 5: Verify MCP authorization

1. Connect an MCP client as a member of the Group that owns the component used
   in the Scaffolder chapter, then approve the request in Backstage.
2. Run `todo.list-for-entity` with that Component's entity reference.
3. Confirm the result contains the onboarding TODOs created by the template.
4. Use a separate client profile, approve the request as a non-owner, and run
   the same tool.
5. Confirm the call returns no protected TODO data. Depending on the app policy,
   this can be an empty result or an authorization error.

The owner should now see the same TODOs through the Component page, Search, and
MCP. If MCP returns more TODOs, confirm that the action calls
`getTodoReadFilter`. If it returns fewer, confirm that the MCP client was
approved by the same user who tested the Component page.

### What you did

You moved the `todo.read` logic into a helper shared by HTTP routes and Actions,
then registered the read-only `todo.list-for-entity` action. You exposed that
action through a focused MCP server and enabled browser-based approval with
Dynamic Client Registration.

An MCP client now sees the same owner-authorized TODOs as the Component page and
Search.

## Going further

A future `todo.create-for-entity` action could call the owner-protected creation
route from the Scaffolder chapter. Actions that change data should clearly say
that they are not read-only and should not be exposed through MCP until their
permission and confirmation behavior has been tested.
