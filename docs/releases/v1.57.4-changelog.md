# Release v1.57.4

Upgrade Helper: [https://backstage.github.io/upgrade-helper/?to=1.57.4](https://backstage.github.io/upgrade-helper/?to=1.57.4)

## @backstage/integration@2.3.0

### Minor Changes

- 7c5d800: SCM URLs whose repository, owner, or reference parts contain path traversal or URL query and fragment delimiter sequences are now rejected by the SCM URL helpers, and the Bitbucket Cloud and Server default branch lookups now apply the same validation.

### Patch Changes

- b0a0298: Gitea location URLs are now rejected when their repository path contains traversal sequences or URL query and fragment delimiters.
- 0c9eda6: The Gerrit and Bitbucket Cloud URL readers now derive the base of their request URLs from the parsed URL rather than from the raw URL string.
- c518d07: When `allowedInstallationOwners` is configured for a GitHub App, installations owned by other accounts are now left out when enumerating the app's installations. This makes the enumeration consistent with how the list is already enforced when installation tokens are issued, so that consumers deriving organizations from the app's installations, such as catalog providers, only see the allowed ones.
- 5ae00ab: When `allowedInstallationOwners` is configured for a GitHub App, the `publicAccess` token fallback now only mints its token from an installation owned by one of the allowed accounts, instead of using the first available installation. This makes the fallback consistent with how the list is already enforced when installation tokens are issued, so that the fallback is always served by an installation within the allow list.

## @backstage/backend-defaults@0.19.1

### Patch Changes

- e10e38b: Azure Blob Storage URLs are now matched against integrations by exact account host, so an integration no longer claims URLs of a storage account whose name merely ends with the configured account name.
- 0c9eda6: The Gerrit and Bitbucket Cloud URL readers now derive the base of their request URLs from the parsed URL rather than from the raw URL string.
- 7c5d800: The GitHub and Bitbucket URL readers now reject URLs whose repository, owner, or reference parts contain path traversal or URL query and fragment delimiter sequences, including in their default branch and commit lookups.
- Updated dependencies
  - @backstage/integration@2.3.0

## @backstage/plugin-auth-backend@0.31.1

### Patch Changes

- 8fa74e1: Made matching of the `allowedRedirectUriPatterns` and `allowedClientIdPatterns` configuration case-sensitive for URL paths, while the host part of a URL stays case-insensitive as required by URL semantics. Redirect URIs and client IDs that differ from a configured pattern only by path casing are now rejected. Wildcards keep working, including in the path, but the literal text of a pattern is matched case-sensitively too, so a pattern such as `https://app.example.com/oauth/*` no longer matches `https://app.example.com/OAUTH/...`.

## @backstage/plugin-auth-backend-module-auth0-provider@0.4.8

### Patch Changes

- 38aca62: The Auth0 provider now includes the configured domain in the cache key used for profiles fetched during token refresh, so that environments pointing at different Auth0 tenants no longer share cached profile entries.

## @backstage/plugin-auth-backend-module-cloudflare-access-provider@0.5.3

### Patch Changes

- 3ef564f: The Cloudflare Access auth provider now caches the user identity information fetched from Cloudflare per access token rather than per user, and no longer than one minute or until the token expires. This makes sure that changes to the identity, such as group membership, are reflected when users sign in again with a new token.

## @backstage/plugin-catalog-backend@4.0.6

### Patch Changes

- 45007f0: The `PUT /locations/:id` endpoint now requires the `catalog.location.delete` permission in addition to `catalog.location.create`. Updating a location that changes its target replaces the location and re-registers the entities that it holds, so it requires the same permissions as the equivalent delete and create operations. Make sure that your permission policies grant `catalog.location.delete` to users who need to update locations.
- Updated dependencies
  - @backstage/integration@2.3.0

## @backstage/plugin-catalog-backend-module-azure@0.3.25

### Patch Changes

- 861126b: Catalog locations constructed by the Azure DevOps catalog module — the entity provider, the `azure-discovery` location processor, and the webhook-driven SCM events — now encode the repository file path as a URL query parameter value. Previously, file names containing characters that are special in a URL query string (such as `&`, `#`, or `=`) could produce a location URL that points at a different file or branch than the one that was discovered. Because the `azure-discovery` processor emitted its locations without any encoding before, locations of that processor for files or branches whose names contain spaces, `+`, or non-ASCII characters change once on upgrade.
- Updated dependencies
  - @backstage/integration@2.3.0

## @backstage/plugin-catalog-backend-module-github@0.14.3

### Patch Changes

- 384b8a3: Catalog location URLs and refresh keys built by the GitHub entity provider now percent-encode the committed file paths and branch names, including the repository's default branch, that they are constructed from, and file paths or branch names that contain `.` or `..` segments are ignored.
- Updated dependencies
  - @backstage/integration@2.3.0

## @backstage/plugin-scaffolder-backend@4.3.1

### Patch Changes

- 8886bd3: Fixed matching of action input values in scaffolder permission policies, including identifiers that are provided as arrays of values, such as the path of the `gitlab:group:ensureExists` action. Conditional policies now apply to every identifier that the array denotes, including the parent groups that `gitlab:group:ensureExists` ensures along the way, so allow-list policies for that action need to allow those parent groups as well. Inputs that denote no identifiers at all, such as an empty array, are now rejected.
- 0862acc: Scaffolder template, fetch and rename actions no longer place their output inside a `.git` directory of the task workspace, matched case-insensitively, so repository metadata there is always provided by the scaffolder's own git operations.
- Updated dependencies
  - @backstage/integration@2.3.0
  - @backstage/plugin-scaffolder-node@1.0.1

## @backstage/plugin-scaffolder-node@1.0.1

### Patch Changes

- 0862acc: The `fetchContents` helper used behind `fetch:plain` and `fetch:template` now rejects fetched trees that contain a `.git` directory, matched case-insensitively. The repository initialization used by scaffolder publish actions now replaces any pre-existing `.git` directory in the source path instead of reusing it.
- Updated dependencies
  - @backstage/integration@2.3.0
